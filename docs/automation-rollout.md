# Offline automation consistency: current Temporal successor

This is a repository-side contract inventory and operator review aid for issue
#42, not a deployment procedure or an automation/security policy change. The
current operator-managed runtime is the **Temporal successor**, outside this
checkout. No current successor source, reviewed source revision/hash lock,

Repository fixtures alone cannot establish that the reported live symptoms are

## Bounded checker

From the checkout, with Python 3 and its standard library only:

```sh
python3 -B scripts/check_automation_rollout.py --repository-only
python3 -B scripts/check_automation_rollout.py
python3 -B scripts/check_automation_rollout.py --demo
```

- `--repository-only`: exit 0 (`repository_ok`) means pinned repository bytes and
  synthetic fixture invariants match. External components remain `not_inspected`.
- Default: exit 1 (`blocked`) without explicit snapshots, even if all repository
  checks pass. This is intentional, not a claim that Temporal is broken.
- `--demo`: reproducible in-memory synthetic inventory: Docs/GitHub hashes match,
  attention is stale, service is missing. Exit 1 is expected. No runtime files
  are read or created. Synthetic matches are not implementation evidence.
- With explicit snapshot inputs: exit 0 (`offline_ok`) means fixture checks plus
  byte identity against the supplied lock only. Exit 1 reports missing/stale or
  unsafe dependencies; exit 2 means invalid/unreadable inventory input. None of
  these statuses establish semantic compatibility or deployment readiness.

The checker reads only the fixed repository reference allowlist in
`scripts/automation-rollout.json` and, when requested, four fixed successor paths.
It bounds reads to 2 MiB per regular file, refuses symlinks/special files below
the selected roots, never imports supplied adapters, and never reads environment
configuration, git metadata, credentials, SQLite, service units or global skills.
It does not walk directories or print file contents, user paths or exception
messages. Its JSON stdout contains allowlisted relative paths, contract names,
hashes, fixed diagnostic statuses and limitations. It performs no writes,
network calls, copying, subprocess/service operations or implicit deployment.
Use `-B` for subprocesses in test/capture commands to suppress Python bytecode.

### Optional sanitized snapshot comparison

Only a separately prepared, nonsecret source snapshot may be passed; **do not
point the checker at a live installation or credential directory**. An independent
reviewer supplies expected SHA-256 values, not a baseline generated automatically
from the same directory being checked. Place these four relative files under a
local snapshot root:

| Component | Snapshot path | Repository contract references |
| --- | --- | --- |
| Docs | `successor/docs.py` | planning generator, structured content, complete creation batch, generator tests |
| Attention | `successor/attention.py` | pure prompt renderer, sender/routing tests, callback tests, synthetic event fixture |
| GitHub | `successor/github.py` | classifier and issue-to-PR static tests (historical policy context only) |
| Service | `successor/service.py` | durable receiver and retry/race tests (reference behavior only), event fixture |

Snapshot lock JSON has exactly this shape, with each placeholder replaced by an
independently reviewed lowercase 64-hex SHA-256:

```json
{
  "schema_version": 1,
  "runtime": "temporal",
  "source_sha256": {
    "successor/docs.py": "<reviewed sha256>",
    "successor/attention.py": "<reviewed sha256>",
    "successor/github.py": "<reviewed sha256>",
    "successor/service.py": "<reviewed sha256>"
  }
}
```

```sh
python3 -B scripts/check_automation_rollout.py \
  --snapshot-root /path/to/sanitized-snapshot \
  --snapshot-lock /path/to/independently-reviewed-lock.json
```

The lock is an explicit input, not an authentication or approval mechanism. The
checker cannot verify its provenance. It does not invent Temporal source hashes
from legacy helpers. Record reviewed revision identifiers and provenance outside
the checker along with the report; the local environment need not have git.
Never record tokens, raw production updates, private documents or personal data.

## Readable formatting and continuation contract

`scripts/fixtures/automation-formatting.json` contains safe synthetic prompt,
HTML/button output, canonical callback and unchanged text Reply examples. IDs,
callback data and context are fake. The callback/reply examples are generated by
the repository reference Store in memory, not copied from a production outbox.
`scripts/automation-rollout.json` pins all referenced bytes and maps them to
Temporal roles. Changes to these pins require explicit review of diffs and tests;
there is deliberately no auto-refresh or copy command in the checker.

### Docs: `successor/docs.py`

Use native TITLE/HEADING_1, 11-point body, 115% line spacing, paragraph spacing,
native bullet/numbered lists, clickable issue URL and monospace paths. Calculate
ranges from rendered UTF-16 text, including non-BMP characters. The creation
fixture's status prefix is `Status: \n\n`; text/style/list requests precede the
single chip insertion at index 9. Exactly three native dropdown options remain:
`review requested`, `changes requested`, `ready for implementation`; creation
starts at `review requested`. A recommendation never changes review state.

The creation batch is an oracle for **new plans only**. Existing documents need
live tab/chip/definition identities, current UTF-16 positions and
`requiredRevisionId`-guarded targeted changes. Preserve registration, locks,
monitor binding, recovery records, comments and native human review/handoff gates.
Never replay creation batches, bulk-restyle plans or select a user-owned state.
The checker validates stored creation JSON; generator tests establish generation
parity. Neither proves actual Google Docs rendering.

### Attention: `successor/attention.py`

Use escaped HTML heading/context link, concise question, 2-5 single-choice
options, exactly one first recommendation, and `Other / write a reply`.
Approval prompts retain decline/cancel. `Other` only invites a text Reply; it is
not an answer. Recommendations, delivery and acknowledgement are never consent.

The legacy event keeps its exact `reply` message, without invented callback
metadata. The callback event has integer `schema_version=1`, unchanged raw
`update` and `callback_query`, and `answer` containing source, persisted
`option_id`, `label` and exact description as `text`. It has **no fabricated
`reply`**. The common question/bot/delivery key, pending chat/user/message IDs,
update ID and issue context remain bound. Callbacks read canonical `answer.text`;
legacy events read canonical `reply.text` only after strict verification.

These examples are **not** an event verifier. External Temporal integration tests
must compare the entire event with the canonical durable outbox and persisted
option/token mapping, raw update, configured bot, private sender/chat and exact
question message. Reject unknown/stale tokens, mismatched descriptions/context,
forged metadata, wrong bot/sender/chat/message, Other as answer and duplicate
continuations. Preserve existing accepted-event/receipt repair rules rather than
creating a new exception. The checker cannot observe any of these runtime gates.

### GitHub: `successor/github.py`

Review the current installation-App comment implementation for exact target,
durable marker/idempotency, persisted comment readback and expected REST Bot
identity (`demik-paseo-bot[bot]` with type `Bot`; GraphQL may normalize the login).
Inspect all relevant producer routes, including cross-target replies, without
assuming an execution can choose arbitrary targets. Unknown delivery stops for
reconciliation, not a personal-token fallback or blind resend. Preserve historical
comments. No live comments are created or rewritten by this work.

Repository classifier/issue-to-PR tests inventory different existing policies;
they do not execute a model or test the Temporal transport. Some still describe
Hub. They are historical context, **not** instructions to deploy Hub, change an
account, export tokens or switch comment channels in the current runtime. Any
policy modernization remains a separate explicit proposal/review; no existing
`.opencode/skills/*/SKILL.md` or automation/security policy is changed here.

### Service: `successor/service.py`

Retain the current sole receiver and task worker. Review canonical first-answer
atomicity, one outbox event, bounded retry deadlines, independent durable UI
acknowledgement/cleanup retries, task locks, journals, durable dispatch receipts
and Temporal idempotency/replay behavior. Do not start another poller/worker,
consume production replies, remove locks or manipulate the bot queue. Keep the
issue-only continuation boundary and all live-state/native approval checks.
Legacy SQLite/Hub tests describe invariants, not Temporal storage architecture.
No Hub receiver, helper bundle or global adapter is copied or restarted.
